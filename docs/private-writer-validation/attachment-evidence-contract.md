# Held existing-attachment evidence contract

This dependent local patch tightens R3/R4 of the October 8 private-writer audit. It does not import or register the held writer in stable upstream, change permissions or preferences, populate any of the 13 null release-evidence records, or resolve the maintainer's live editor, replica-identity and independent-device questions. Attachment removal/replacement remains refused.

## Complete evidence and its boundary

`attachment-evidence.h` is an original Foundation/CommonCrypto/POSIX substrate. Its independently compilable fixture contains no NotesShared load, store access, actions or preference changes. One descriptor-bound read hashes a regular file only when path/descriptor identities, size, mtime and ctime agree before and after the read. The complete read length must equal the descriptor size. A cumulative 512 MiB budget applies per native snapshot capture; exactly-at-budget and zero-byte regular files are valid. Budget exhaustion, unavailable/unreadable files, links/nonregular files and detected drift refuse. Equal size/time and repeated inaccessible-state sentinels are never byte evidence.

The native snapshot covers every row in the target note's attachment and inline-attachment ownership relationships, including hidden, orphaned and tombstoned rows. It binds stable row identity, entity, every supported nontransient stored attribute, ownership and other stored relationship identities, each attachment's media row and required media bytes, and identified glyph order/type/count. Exact tagged Foundation scalars avoid rounded date/number comparisons; stored data is hashed incrementally. Missing ownership relationships, duplicate identifiers (including across attachment and inline namespaces), unidentified/dangling glyphs and unsupported stored classes refuse.

The explicit policy excludes transient attributes. Unknown decoded transformables refuse rather than disappear from the evidence. A top-level row without media is accepted as byte-free only for the audited table and URL-card kinds; other types with missing media refuse. A media relationship always requires complete, available file bytes. This conservatively reduces availability for cloud placeholders and unsupported attachment representations. It does not promise arbitrary private model/preview-resource layouts whose required files cannot be established by the supported schema.

The reviewed receipt includes the exact version floors. During a single apply, the already declared `minimumSupportedNotesVersion` floor may rise, never fall. This exception does not permit a changed floor between preview and apply: the reviewed receipt comparison is exact.

## Plan and apply compatibility

Read-only edit and existing-note compose plans return `attachmentSnapshot` (`a1:` plus 64 lowercase hex digits), `attachmentEvidencePolicy`, and completeness counters. Apply requires that receipt as `ifAttachmentSnapshot`, independently of the note's `r1:` token. Edit request digests are now `p4:`; compose request digests are now `c2:`. They bind the receipt and its completeness/version-floor policy in addition to the prior request, revision, scope and new-input-file fields. Older `p2:`, `p3:` and `c1:` plans do not satisfy the stronger contract. Obtain a fresh plan; deterministic digests do not authenticate human approval.

Apply recaptures before object/file materialization and compares the reviewed receipt, including for a no-op. A fresh read-only stack recaptures immediately before materialization; the preserved set is checked again in the writing context and through another fresh persisted capture before save, then through fresh readback after save. Created compose objects are the only excluded new identities. Unavailable evidence refuses before materialization when found at the initial capture; later evidence/drift failures retain the existing early-save and committed/indeterminate reporting. A detected readback failure after a successful save is committed, never reported as a rolled-back refusal.

Public create has no existing target at preview time and does not accept `ifAttachmentSnapshot`. Its `c2:` plan binds the declared new-note/empty-attachment baseline, destination, title and captured new-file hashes before Notes.app creation. After creation, an internal existing `compose_note` read-only plan binds the new identity/revision and complete empty attachment set; unexpected objects or a revision change refuse. The append applies that internal plan's receipt/digest. This is a binding sequence for a newly created note, not an apply-generated substitute for an existing note's reviewed receipt. Running Notes policy and cleanup/uncertainty behavior remain in place.

Table service/tool schemas additionally require the `a1:` receipt from `native-read-tables` or the deletion/prune dry run. These TypeScript changes depend on the coordinated native table receipt/preservation patch. Its full pre-apply receipt includes the selected table; only the exact intended selected-table identity is excluded from within-call unrelated-object preservation. A fresh table read is needed before chaining another write. The table's `t1:` token continues to protect its selected CRDT.

Other private writer actions have not acquired this reviewed snapshot contract. Extending it to checklist/highlight/link-card, Paper, destructive repair or cross-note actions requires their own coordinated plan/read/apply and allowed-delta design. Do not describe R4 as covering every held writer action.

## Build integrity and fixture scope

Setup, handshake manifests and installation inspection now hash the packaged writer's quoted local source closure, including both evidence/preservation headers when included. Literal local includes are discovered with string/character/line-comment aware parsing and line-splice handling; unsupported macro includes, exotic names and paths escaping the source directory refuse. System/framework headers remain external. Single-source fake writers keep their fixture checksum convention. Existing source caches still compare the manifest's source and binary hashes before dispatch; no protocol/action/gate was added.

Pure fixtures exercise small cumulative budgets, the exact boundary, equal-size/mtime changed bytes, missing/unreadable/nonregular/link files, short/growing reads, descriptor/path drift, exact stored scalars, snapshot ordering and row/media/inline/orphan/glyph mutations. Client fixtures verify required receipt forwarding, legacy token rejection, digest binding and create lifecycle behavior. Source checks pin capture/compare ordering. These are synthetic/pure evidence; they neither reproduce a live loss nor establish live Notes compatibility. Real generated-store execution is separately coordinated by the parent review task. No live or copied-store test ran as part of this patch preparation.
